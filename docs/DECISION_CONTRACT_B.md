# Политика обнаружения B для A и C

18.10.2026. B принимает поправку C `2628639` и уточнение `601ead1` из `docs/ADAPTER_REVIEW_C.md`. Ожидание ответа организаторов отменено. Прежний decision-policy.draft.v1 заменён: не требуется доказывать отсутствие всех возможных нарушений или блокировать сервис из-за неизвестного факта/неподдерживаемого класса.

Основание трактовки ТЗ — перечитывание C и прямое указание пользователя. B не заявляет независимую проверку оригинального ТЗ в этом этапе. Публичная схема сохраняет два вердикта; сервис обнаруживает признаки возможного нарушения и помогает человеку, а не выносит окончательное правовое заключение.

## Семантика двух вердиктов

| Ситуация | Решение |
| --- | --- |
| Технически выполнены выбранные детекторы, есть обоснованное событие | violation: обнаружены признаки возможного нарушения; C проверяет исходные JPEG перед публичной выдачей |
| Технически выполнены выбранные детекторы, обоснованных событий нет | no_violation: признаки не обнаружены данным решением, список событий пуст |
| После доступного уточнения остаются null, конфликт или недостаточные основания | Кандидат не подтверждается, причины сохраняются локально. Если других подтверждённых событий нет, успешный полный проход даёт no_violation |
| Детектор не запускался, сорван/неполон проход, техническая ошибка или истёк дедлайн | Отрицательный ответ запрещён; технический сбой C обрабатывает как failed. Неготовую конфигурацию выявлять до приёма задач |

Unknown не превращается в false. Неизвестность другого эпизода не отменяет обоснованное обнаружение. Отрицательный ответ не утверждает корректность всех действий или отсутствие непокрытых типов. Ограничения и поддерживаемые классы публикуются при сдаче; пропуски/ложные тревоги измеряются, а не оправдываются смыслом no_violation. Пустые assessments отдельно не доказывают выполнение детекторов.

## Реализованная функция B

`app.rules.finalize_detection(report, assessments, search, *, supported_rule_ids, registry=None)` реализует `detection-policy.v1`. Она вызывает существующий evaluate, не анализирует свободный текст и не читает разметку. Старый evaluate остаётся промежуточным оценщиком, не фабрикой C.

Входы:

- Выходной observations.v1 A со всеми уточнениями, непустым job_id, complete=true и coverage_scope=full_video. Это полный технический проход запланированных окон, не гарантия видимости каждого действия.
- assessments по RULES_B; все пакеты относятся к явно заданному непустому уникальному supported_rule_ids.
- Реестр с проверенными правилами этого охвата. Hypothesis нельзя считать исполнившимся отрицательным детектором: функция отклоняет такой запуск даже при пустых assessments.
- search — предлагаемое A/C расширение diagnostics.search с квитанцией выполнения. Ещё не реализовано в worker A; согласование его производителя остаётся задачей A/C.

```json
{
  "schema_version": "detector_execution.v1",
  "job_id": "synthetic-job",
  "detector_runs": [{
    "rule_id": "cashier_leaves_service",
    "detector_version": "synthetic-only",
    "status": "complete",
    "processed_window_ids": [0],
    "refinement_status": "completed"
  }]
}
```

На каждый настроенный класс нужен ровно один run. processed_window_ids содержит каждый window_id выходного report ровно один раз: детектор этого класса действительно обработал обзор и добавленные уточнения. refinement_status=completed означает технически завершённые запрошенные уточнения; not_needed — уточнение не назначалось. Неразрешимая семантическая неизвестность совместима с completed. Pending, пропущенные окна, сбой, отсутствие версии/класса, другой job_id или interval вместо full_video блокируют финализацию. Ограничение числа уточнений допустимо как заранее заданная и измеренная политика; нельзя обозначать прерванный запрос completed.

Квитанцию формирует A только после выполненных вызовов, C проверяет соответствие реальному запуску. Нельзя построить её из пустого списка пакетов, копированием ID окон или из одного report.complete. Проверка структуры B сама по себе не доказывает истинность квитанции; нужны тесты producer A и реальный сквозной прогон. Точность и полнота поиска проверяются отдельно.

Выход detection_result.v1: job_id, complete, verdict, supported, unresolved, policy_version и negative_policy_version=detection-policy.v1, supported_rule_ids, registry_version/sha256, public_verdict_ready=false. Unresolved содержит ключ эпизода и коды причин; факты не переписываются. Конфликт service_in_progress=true и service_completed=true на один момент сохраняется как conflicting_service_state, а не обычный rejected. Противоречащие источники A сохраняет в diagnostics и не передаёт как уверенные bool; C проверяет их до финализации. Другие пары без доказательства противоречия автоматически конфликтом не объявляются.

Это внутренний результат B, **не RuleDecision C и не разрешение production**. Функция не проверяет происхождение каждого bool, содержимое local_context, качество эпизодов или JPEG. A формирует факты и диагностику, C проверяет bundle/источники/конфликты и реализует адаптер с извлечением кадров. public_verdict_ready=false сохраняется до отдельной интеграции и проверки качества; его нельзя просто переименовать в true. Строка версии политики также не подтверждает её валидацию на данных.

## Оболочка A и ограничения

B принимает направление assessment_bundle.v1 C: report/assessments/diagnostics, episode diagnostics и fact_sources отдельно от facts. Происхождение visual/local_context/mixed/unknown; при mixed нужны оба источника, при unknown — причина. Согласовать с A единое имя поля origin. Контекстные ссылки не заменяют визуальные; координаты после display rotation и область применимости проверяются локально. Ручная настройка каждого нового публичного видео не должна быть обязательным этапом API: неизвестный контекст даёт null, не выдуманную геометрию.

Первый юридический кандидат — cashier_leaves_service; смена внимания не доказывает физический уход. Критерии и текущие неизвестные: [FACT_DEFINITIONS_B.md](FACT_DEFINITIONS_B.md). Источник нормы не доказывает работу детектора.

## Готовность и следующая проверка

Функция проверяется синтетическими тестами: положительное обнаружение, трудный отрицательный случай, неизвестность, конфликт, пустые пакеты с квитанцией, пропущенные окна/ошибка/чужое задание, неактивный реестр. Это не реальные результаты A.

Реестр остаётся hypothesis/validated_on_local_cases=false. Локальные положительные, сложные отрицательные и неоднозначные примеры ещё не подтверждены; нет реализации квитанции A и измеренной точности. План — [LOCAL_VALIDATION_B.md](LOCAL_VALIDATION_B.md). Оцениваются и ложные отрицательные при no_violation на неизвестных эпизодах, доля null/конфликтов, пропуски/FP, временная точность и полный бюджет. Неоднозначные человеческие метки не считать заведомыми отрицательными. Активация после проверки — отдельное решение команды. Ответ организаторов больше не является блокером.
