# Runpod: запуск API и GPU-обработчика

Эта инструкция запускает существующую установку `/workspace/forte`: API из
`.venv`, Qwen3-VL-32B-Instruct-FP8/vLLM и CV-модели из `.venv-vllm`.
Установка зависимостей и загрузка весов — отдельный этап из
[RUNPOD_SETUP.md](RUNPOD_SETUP.md). Скрипт ничего не скачивает и не создаёт ключи.

Выбрана настоящая фабрика `app.jobs.unified:create_signs_processor` и политика
[signs-targeted.v1](SIGNS_POLICY.md). Она выдаёт признаки возможных нарушений
в реализованной области поиска; не объявляет окончательное юридическое решение
или измеренную точность. Для этой явно выбранной фабрики release-файл не нужен.
Реестр не переводится в reviewed, а стандартная фабрика `create_processor`
сохраняет собственные требования к release.

## Перед запуском

- Код, `.venv`, `.venv-vllm` и локальные веса уже установлены на сервере.
- В существующем `/workspace/forte/.env` настроены разные `FORTE_API_KEY` и
  `FORTE_WORKER_KEY` длиной не менее 32 символов. Приложения читают его через
  `load_dotenv(override=False)`; скрипт не выполняет `.env` как shell-код.
  Уже экспортированные переменные имеют приоритет над `.env`.
- Нужны Linux, Bash >= 4.3, `setsid`, `flock` и `ps`.
- Предыдущий API/worker и отдельный GPU-бенчмарк завершены их владельцем.
  Не запускать второй загрузчик моделей поверх текущего бенчмарка.
- Порты 8000 и 8002 свободны. Скрипт откажется запускаться при занятом порте,
  другом экземпляре этого supervisor или существующем API/worker того же checkout;
  чужие процессы он не останавливает. GPU-процессы других инструментов не завершает
  и их отсутствие автоматически не удостоверяет.

Из терминала сервера:

```bash
cd /workspace/forte
bash -n scripts/run_runpod.sh
bash scripts/run_runpod.sh
```

Скрипт остаётся на переднем плане. Для работы после отключения SSH можно выполнить
эти же команды внутри уже установленного `tmux`; запускать только одну сессию
сервисов. Не применять `bash -x`, не выводить `.env` и не копировать частные логи
в облачные помощники или внешние системы журналирования.

## Что именно запускается

Сначала экспортируется `config/runpod-l40s-vllm.env`, затем явно фиксируются
offline/telemetry-настройки и `FORTE_STORAGE=/workspace/forte/.runtime`.
Дополнительно задан `VLLM_ENABLE_V1_MULTIPROCESSING=0`: внешний queue worker уже
создаёт дочерний процесс модели через spawn. Эта топология проверена отдельным
реальным GPU-прогоном с синтетической генерацией; результаты и границы проверки приведены ниже.

Эквивалентные команды компонентов ниже приведены для понимания процесса.
**Не выполнять их параллельно с supervisor.**

```bash
.venv/bin/python -m app.api \
  --public-host 0.0.0.0 --public-port 8000 \
  --worker-host 127.0.0.1 --worker-port 8002

.venv-vllm/bin/python -m app.jobs.worker \
  --coordinator http://127.0.0.1:8002 \
  --worker-id l40s \
  --factory app.jobs.unified:create_signs_processor \
  --startup-timeout 360 \
  --work-dir /workspace/forte/.runtime/worker
```

API создаёт отдельные public/private процессы. Worker отдельно загружает настоящие
модели и регистрируется у координатора после успешной инициализации. Скрипт сначала
ожидает TCP-слушатели API не более 30 секунд, затем запускает worker. Таймаут
360 секунд относится к загрузке модели, а не к обработке каждого задания.

В Runpod наружу направляется только HTTP-порт **8000**. Порт **8002** привязан к
`127.0.0.1` и не должен добавляться в публичный proxy. Адрес публичного proxy берётся
из текущего Runpod; эта инструкция не публикует сервер и не подтверждает работу
внешнего маршрута.

## Проверка готовности без вывода данных

`/healthz` подтверждает только работу API. Для состояния обработчика служит
`GET /api/v1/readiness` с `X-API-Key`: до регистрации модели ожидается HTTP 503,
при готовом worker — HTTP 200. Это техническая готовность, не оценка точности.

Следующая локальная проверка загружает ключ из `.env` в память и выводит только
HTTP-код и число готовых обработчиков; ключ не попадает в аргументы `curl`:

```bash
cd /workspace/forte
.venv/bin/python - <<'PY'
import os
import httpx
from dotenv import load_dotenv

load_dotenv(override=False)
with httpx.Client(trust_env=False, timeout=5) as client:
    response = client.get(
        'http://127.0.0.1:8000/api/v1/readiness',
        headers={'X-API-Key': os.environ['FORTE_API_KEY']},
    )
    state = response.json() if response.status_code in (200, 503) else {}
    print({'http_status': response.status_code,
           'ready': state.get('ready'),
           'ready_workers': state.get('ready_workers')})
PY
```

После технической готовности нужен отдельный сквозной тест по
[CONTRACTS.md](CONTRACTS.md): upload MOV → durable queue → реальный GPU →
`done`/`failed` → проверка исходных JPEG и реальных PTS. Видео, содержимое ответа,
описания и JPEG остаются внутри разрешённой среды. Наружу для отчёта передаются
только агрегированные технические метрики. Неполная обработка и сбой должны дать
`failed`, а не успешный `no_violation`.

## Остановка и диагностика

Нажать Ctrl+C в терминале supervisor либо отправить SIGTERM **его текущему PID**.
Для API и worker созданы отдельные process groups; supervisor направляет TERM
обеим своим группам, включая spawn-потомков, ждёт до 10 секунд и завершает
оставшихся через KILL. При неожиданном выходе любого основного процесса
останавливается и второй. Повторного автоматического запуска здесь нет.
SIGKILL самому supervisor не позволяет выполнить cleanup; после такого аварийного
завершения сначала проверить оставшиеся процессы, а не обходить отказ запуска.
Остановка группы обязательна: в интеграционной проверке SIGTERM только родителю
`app.api` оставил два дочерних процесса API. Поэтому этот launcher завершает всю
собственную группу, а не только PID родителя.

Логи каждого запуска: `artifacts/server-setup/run-<UTC>-<unique>/api.log` и
`worker.log`. Новые каталоги и файлы создаются с закрытыми правами (`umask 077`).
Это частные, исключённые из Git артефакты; возможные трассировки просматриваются
локально. Supervisor печатает только служебные сообщения, не содержимое логов.
Остановка не удаляет `.runtime`, задания или загруженные файлы; поведение
незавершённой аренды определяется существующим durable queue.

## Статус проверки и передача следующему участнику

Подготовлен воспроизводимый launcher; его полный Linux lifecycle ещё не проверен.
Проверка `bash -n scripts/run_runpod.sh` выполнена через Git Bash на Windows: exit 0;
файл имеет LF без BOM. Модели и сервисы при этой проверке не запускались.

Интеграционные проверки основной задачи подтвердили следующие технические результаты:

- Daemon `ProcessorProcess` с настоящими Qwen3-VL-32B-Instruct-FP8 и CV-моделями:
  синтетическая генерация прошла, использовались `InprocClient` и `UniProcExecutor`;
  холодная загрузка 168,237 с, полный bootstrap 174,875 с.
- После штатного close память GPU освободилась, GPU-процессов не осталось.
- Повторная загрузка заняла 61,013 с. При тестовом deadline 1 с принудительное
  завершение заняло 1,634 с; память освободилась, дочерних GPU-процессов не осталось.
- Внешние проверки публичного API: 6 из 6 прошли.

Эти отдельные проверки не подтверждают полный анализ MOV через новый launcher,
`create_signs_processor`, очередь и JPEG/PTS. Запуск настоящего worker и сквозная
проверка выполняются основной интеграционной задачей; их результат здесь пока не
заявлен. Проверка завершения всей группы именно этим shell-supervisor также остаётся
отдельным шагом. Подробный статус хранится в [INTEGRATION_STATUS.md](../INTEGRATION_STATUS.md).

Следующий участник фиксирует версии кода/конфига, холодный startup, readiness,
время всего запроса, terminal status, проверку JPEG/PTS и отсутствие оставшихся
дочерних GPU-процессов после остановки. Точность обнаружения оценивается отдельно.
