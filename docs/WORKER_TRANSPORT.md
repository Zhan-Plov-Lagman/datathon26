# Предлагаемый стык C → A/B, версия 1

Реализация C находится в `app/jobs/`. Код A подключён из `feature/ml-worker` без изменений. Этот документ фиксирует **предложение для проверки A/B**, а не утверждение, что B уже согласовал или реализовал интерфейс. Публичная схема жюри не изменена. Зависимости координатора изолированы в `requirements-api.txt`; GPU-зависимости A не изменены. Общий Pillow оставлен 12.1.0.

## Подключение правил B

`FORTE_RULES_FACTORY=<module>:<function>` указывает фабрику без аргументов. Она возвращает объект:

```python
class ReviewedEvaluator:
    reviewed = True  # Только после реальной проверки реестра.

    def evaluate(self, report, *, video_path, worker, deadline):
        ...
```

`report` — настоящий `observations.v1` от A, весь ролик. `deadline` — абсолютный `time.monotonic()`, оставшийся общий бюджет. `worker` — уже загруженный `LocalGPUWorker` A; `worker.refine(video_path, report["job_id"], intervals, deadline=deadline)` уточняет интервалы в общем бюджете. B выполняет проверку правил, исключений и дедупликацию; при отсутствии подготовленных правил, технической неполноте или невозможности выдать обоснованный результат поднимает исключение. Пустые наблюдения сами по себе не означают отрицательный вердикт.

Возвращаемая структура проверяется `app.jobs.pipeline.RuleDecision`:

```python
{
    "complete": True,
    "rules_reviewed": True,
    "rules_version": "<версия проверенного реестра>",
    "supported": [
        {
            "rule_id": "<существующее правило из реестра B>",
            "type": "<тип из каталога B>",
            "anchor_sec": 1.0,
            "description": "<наблюдаемое действие + основание из реестра, документ, пункт, URL>",
            "evidence_timestamps": [1.0]
        }
    ]
}
```

Пример описывает форму, не действующее правило. В `supported` передавать только подтверждённые события после уточнения. Один или несколько событий допускаются. При пустом списке обязательно дополнительное поле `negative_policy_version`: непустая версия проверенной B политики отрицательного решения по всему ролику. Без неё C отклоняет результат. Для положительного решения поле необязательно. Для неизвестных/невидимых ситуаций B отвечает за правила принятия решения согласно ТЗ и валидации; C не додумывает юридический вывод. Наличие строки версии не доказывает качество политики: её проверку на реальных примерах выполняет B.

Проверено 18 октября: B `f01e643` предоставляет `evaluate(report, assessments, registry=None)` и `rule_results.v1`, а не эту фабрику. Все пять правил в реестре имеют статус `hypothesis`, `public_verdict_ready` всегда `false`. C намеренно отклоняет этот результат; извлекать из него пустой `supported` и объявлять `no_violation` нельзя. Для ухода B опубликовал `FACT_DEFINITIONS_B.md` и нормативное решение `LEGAL_DECISION_B.md`; фактическое извлечение, локальная валидация и политика ещё необходимы. `client_interaction_switch` не является подтверждённым нарушением. После согласования C подключит адаптер. `negative_policy_version` — уточнение внутреннего контракта C для совместной проверки A/B; публичные поля жюри не меняются. Точный статус — `INTEGRATION_C.md`.

Адаптер C извлекает исходные JPEG одним проходом через A `worker.evidence(video_path, requests, deadline=deadline)`, проверяет диапазоны времён, JPEG и согласованность вердикта, добавляет версии модели/правил. C не может технически доказать юридическую корректность `reviewed=True`; достоверность реестра, цитат и выводов проверяет B. Если интерфейс B будет другим, изменить адаптер C после проверки фактического кода, не переписывать модуль B.

## HTTP внутри сети команды

Закрытый сервер — отдельный процесс и порт 8001. Все запросы требуют отдельный `X-Worker-Key`. Эти маршруты **отсутствуют** в публичном приложении на 8000.

| Метод / путь | Данные | Результат |
| --- | --- | --- |
| POST `/internal/workers/heartbeat` | `worker_id`, `ready`, `pipeline_version` | `{"ok":true}` |
| POST `/internal/jobs/claim` | те же поля; только готовый обработчик | 204 без работы; иначе lease |
| GET `/internal/jobs/{id}/file` | заголовки `X-Worker-Id`, `X-Attempt-Token` | исходные байты MOV |
| POST `/internal/jobs/{id}/heartbeat` | `worker_id`, `attempt_token` | оставшийся бюджет |
| POST `/internal/jobs/{id}/complete` | `worker_id`, `attempt_token`, `result` | атомарное завершение |
| POST `/internal/jobs/{id}/fail` | те же идентификаторы, `code`, `retryable` | ограниченный повтор или `failed` |

Lease содержит `job_id`, случайный `attempt_token`, номер `attempt`, `remaining_sec`, `lease_sec`, `download_path`. Токен попытки не помещать в URL и логи. Heartbeat не продлевает общий дедлайн. Время `remaining_sec` позволяет не требовать точной синхронизации часов GPU и C. GPU начинает отсчёт до HTTP claim, чтобы учесть сетевую задержку консервативно.

Внутренний результат — `app.api.schema.AnalysisResult`, `schema_version: analysis.v1`, `analysis_kind: rules_evaluated`, `complete: true`, `coverage_scope: full_video`, `rules_reviewed: true`, `duration_sec`, `model_id`, `model_revision`, `rules_version`, `pipeline_version`, `verdict`, `violations` и `rule_ids` в порядке событий. Для `no_violation` обязателен `negative_policy_version`, переданный из решения B. Сырые `observations.v1` и `rule_results.v1` отклоняются с 422. Публичный GET отдаёт только поля из ТЗ.

Ошибки: `analysis_failed`, `invalid_video`, `deadline_exceeded`, `worker_unavailable`. Тексты исключений, пути и описания сцен не отправляются в ответ ошибки. Невалидный результат отклоняется, после чего штатный worker отправляет `fail`; зависший/исчезнувший worker обнаруживается по аренде. Любой stale heartbeat/результат получает 409, неизвестное задание — 404. Повтор complete после принятия также 409; первый сохранённый результат остаётся неизменным.

Штатный клиент `python -m app.jobs.worker` загружает модель до объявления готовности, сохраняет один GPU-процесс между успешными заданиями, посылает heartbeat, ограничивает время снаружи, не выводит модельные ответы. `--factory` служит расширению интеграционного адаптера; синтетические фабрики существуют только в `tests/api/fakes.py` и не являются режимом рабочего сервиса.

## Что проверить вместе

1. A/B подтверждают интерфейс фабрики и `evaluate`, фиксируют ревизии и проверенные зависимости на Python 3.12.
2. На одном GPU проходит настоящий MOV: API → очередь → A → B → исходный JPEG → GET.
3. B вручную проверяет время, исходный кадр, применимость правила, исключения и отсутствие ложного отрицательного результата.
4. Измеряется весь путь, включая загрузку, очередь, повторные просмотры и ответ; затем подключается второй worker с уникальным ID.
5. Проверяются отказ, повторная выдача и два одновременно загруженных ролика на фактическом оборудовании.
