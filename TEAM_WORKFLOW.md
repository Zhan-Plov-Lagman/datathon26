# Совместная работа трёх участников

У команды три ноутбука: A и B с RTX 4050, C с RTX 3050. Буквы обозначают рабочие роли; команда подставляет имена при распределении. Дедлайн — 18 октября 2026 года, 12:00 по Кызылорде. Рабочий сервис должен быть готов раньше дедлайна, чтобы осталось время на внешний прогон API.

Все общие задачи, контракты, код и решения ведём в этом репозитории. Файл `artifacts/FORTEBANK_PIPELINE_LOCAL.md` — локальная подробная копия аудита, для координации читать его не требуется. Конкретные данные каждый получает из источника организаторов и проверяет локальным скриптом.

Для работы с ИИ каждый открывает клонированную папку в своём редакторе и даёт помощнику текст задания из `prompts/ROLE_A.md`, `prompts/ROLE_B.md` или `prompts/ROLE_C.md`. Прикреплённый отдельно TEAM_WORKFLOW.md не заменяет доступ к репозиторию. Если помощник не читает AGENTS.md автоматически, явно попросить его прочитать. Каждый работает в ветке своей роли, показывает выполненные проверки и передаёт рабочий результат через Git. Облачный помощник пишет код; анализ банковских кадров выполняют только локальные модели.

| Кто | Ответственность | Область будущего кода | Первый результат |
| --- | --- | --- | --- |
| A, RTX 4050 | Локальная модель, декодирование, наблюдения, таймкоды, доказательства | `app/video/`, `app/inference/`, `app/evidence/`, GPU-обработчик | Один ролик анализируется полностью и даёт исходные кадры |
| B, RTX 4050 | Каталог событий, нормативные правила, оценка, эксперименты | `app/rules/`, `evaluation/`, `config/rules.yaml` | Проверенные правила и таблица ошибок базовой версии |
| C, RTX 3050 | API, сохраняемая очередь, интерфейс, сеть, сборка релиза | `app/api/`, `app/jobs/`, `web/`, инфраструктура | Загрузка и опрос задания доступны через публичный URL |

Пути в таблице — разделение будущей реализации, соответствующие модули пока не созданы. Общие файлы зависимостей и настройки запуска меняет C после согласования с A и B. A и B проверяют спорные события вместе. C отвечает за интеграцию, каждый проверяет свой компонент и его стык с остальными.

**Что сделать в первые 20 минут.**

1. Каждый клонирует репозиторий, получает данные и выполняет `docs/DATA_SETUP.md`.
2. Зафиксировать роли A, B, C и приватно обменяться сетевыми адресами компьютеров. Секреты и пароли в Git не писать.
3. Прочитать `docs/CONTRACTS.md` и согласовать его до независимой реализации.
4. C выбирает единый способ запуска и место координатора. На старте достаточно одной рабочей GPU; второй обработчик подключается после полного одиночного сценария.
5. B фиксирует группы дубликатов и разделение выборки до подбора промптов. Точные метки и имена отложенных файлов остаются в локальных артефактах команды.

**Интеграционные рубежи.**

| Рубеж | Кто сдаёт | Условие |
| --- | --- | --- |
| Контракт | Все | Одинаково понимаются статусы, вход и выход модулей |
| Одиночный полный цикл | A + C | Настоящий MOV через API до результата без ручного вмешательства |
| Обоснованное событие | A + B | Наблюдение, время, исходный кадр и проверенное правило согласованы |
| Два обработчика | A + B + C | Два ролика завершаются независимо, результат не смешивается |
| Релиз | Все, координатор C | Пройден чеклист из общего пайплайна |

Каждые 60–90 минут объединять небольшой рабочий результат. В общем чате достаточно трёх сообщений от каждого: что работает, что мешает, что необходимо от другого участника. Изменение схемы сначала обсуждается с её потребителями и одновременно отражается в `docs/CONTRACTS.md`.

**Порядок работы с Git.**

Использовать короткие ветки `feature/ml-worker`, `feature/rules-eval`, `feature/api-ui`. `main` сохраняет последнюю интегрированную версию. Не редактировать одновременно чужие области без договорённости; общие файлы согласовывать с C.

```powershell
git switch main
git pull --ff-only
git switch -c feature/ml-worker
# Внести изменения в свою часть.
git add -- app/inference app/video
git diff --cached --stat
git diff --cached
git commit -m "Add local video observations"
git push -u origin feature/ml-worker
```

Команды `git add` в примере применять после создания соответствующих каталогов. Перед переключением ветки сохранить работу коммитом. Не применять `git add .` без просмотра состава, не делать force push в `main`. Перед объединением C получает актуальную ветку, проверяет стык и проводит быстрый сквозной сценарий. Объединение через pull request или обычный merge без перезаписи истории.
