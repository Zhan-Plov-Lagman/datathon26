## История проверки 17 октября

Проверено 17 октября 2026 на Python 3.12.14 ноутбука A. Источники: A `dbbc4cd`, B `578a6af2b5fb1b2f0f978138d65524fd37be7dbb`, C `0b5af3a80c1cb5cae9a8df996bf1bdeb180c7d12`. Ветки B/C не слиты и не изменены: выбранные исходники прочитаны из Git в игнорируемую `.cache/peer-contracts`.

**Что подтверждено.** Пять синтетических интеграционных тестов прошли за 13,499 с:

- Настоящий валидатор B принимает отчёт, полученный через A `LocalGPUWorker` на синтетическом MOV. Реальное правило B со статусом `hypothesis` не становится `supported` даже при полном синтетическом пакете фактов.
- Настоящий `IntegratedProcessor` C вызывает A, тестовый адаптер вызывает B и A `refine`, затем C получает исходный JPEG через A `evidence` и валидирует результат своей схемой.
- Повреждённый MOV остаётся исключением; следующий корректный запрос проходит. `WorkerBusy` также не превращается в отрицательный вердикт. Непроверенные правила отклоняются.
- Результат нынешней функции B действительно не соответствует `RuleDecision` C. Тест фиксирует этот разрыв, а не считает формат готовым.

Для положительного сценария существуют только синтетические observer, реестр и адаптер внутри `tests/integration/test_peer_contracts.py`. Они не являются фабрикой сервиса и не применялись к банковским видео. Проверены Python-интерфейсы и JPEG; HTTP, очередь, удалённый транспорт и качество зрения в этом тесте не проверялись.

Дополнительно два ранее сохранённых настоящих отчёта A (1 и 15 окон) локально прошли `validate_report` B. Проверка с пустым списком пакетов фактов вернула `requires_review: true`, `public_verdict_ready: false` в обоих случаях. Содержимое сцен не выводилось. Это проверка совместимости схемы, а не результат обнаружения нарушения.

**Что мешает настоящему полному сценарию.**

| Стык | Текущее состояние | Необходимое действие |
| --- | --- | --- |
| A → B | Наблюдения совместимы; автоматических `local_assessments` нет | A/B согласуют визуальное значение каждого выбранного предиката и проверяют локальный извлекатель фактов: bool/null, ссылки на наблюдения, действительный опорный кадр, идентификатор эпизода. Не получать факты по ключевым словам описания или по меткам организаторов. |
| B → C | B: `evaluate(report, assessments, registry)` → `rule_results.v1`. C: фабрика объекта с `reviewed` и `evaluate(report, *, video_path, worker, deadline)` → `RuleDecision` | B/C реализуют адаптер после согласования источника фактов. `registry_version` сопоставляется с `rules_version`; доказательства выбираются по подтверждённым наблюдениям. Нельзя просто переименовать поля и объявить результат готовым. |
| Готовность правил | Все продуктовые классы B — `hypothesis`; `public_verdict_ready` всегда false | B завершает локальную проверку применимости классов, исключений и трудных отрицательных примеров. Не выставлять `reviewed=True` только ради запуска C. |
| Отрицательный вердикт | Пустые пакеты и `candidate` не дают отрицательного заключения B; C выдаёт `no_violation` для принятого пустого `supported` | B/C фиксируют политику завершённого отрицательного решения и неопределённости. Не превращать отсутствие извлечённых фактов в автоматический отрицательный ответ. |

`full_sequence_visible` нельзя вывести из `complete` или из успешного плотного просмотра. Общие ограничения видимости A нельзя удалять, чтобы обойти блокировку B: B должен определить необходимые наблюдения и получить достаточные локальные доказательства. Эти вопросы относятся к качеству фактов и правил, а не к несовместимости JPEG или Python-сигнатур A/C.
