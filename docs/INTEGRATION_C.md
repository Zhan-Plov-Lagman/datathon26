# Интеграция A/B/C

Обновлено 18 октября 2026. Код A `c224ec8` и основная ветка B `2ac8f3c` объединены в C. Текущий согласованный контракт, проверки и ограничения — [ADAPTER_REVIEW_C.md](ADAPTER_REVIEW_C.md). Старые обсуждения доступны в Git.

## Поток обработки

API сохраняет MOV и задание → worker A выполняет analyze и assess с уточнением → C проверяет report/источники/контекст → B применяет detection-policy.v1 → C строит RuleDecision, получает исходные JPEG и возвращает схему жюри. Техническая ошибка даёт failed; успешный анализ — violation либо no_violation в смысле «признаки не обнаружены данным решением».

Реализация C: [EVALUATOR_C.md](EVALUATOR_C.md). HTTP и внутренняя схема: [WORKER_TRANSPORT.md](WORKER_TRANSPORT.md). Принятая архитектура — весь сервис на A без VPN, запуск по [SINGLE_LAPTOP.md](SINGLE_LAPTOP.md).

## Осталось до готовности

1. A/B проверяют реальные примеры, область применимости контекста, уточнение и качество; фиксируют фактические версии и результаты приёмки. Подборка по заметкам не равна проверенной разметке. Другой ракурс не получает старую геометрию автоматически.
2. C создаёт конфигурацию принятого релиза и фабрику; текущий hypothesis-реестр не активировать. Код evaluator готов, конфигурации реальной приёмки ещё нет.
3. Провести настоящий полный MOV-путь на A и измерить время, включая загрузку/очередь. Раздельные замеры A на длинном примере указывают риск превышения текущего бюджета C 240 с; полного измерения нет.
4. Настроить публичный URL, проверить API извне на 5+ видео и передать адрес/ключ жюри. Внутренний порт 8001 и worker key не публиковать.

После первого работающего сценария проверять дополнительный GPU и параллельную нагрузку. main не обновлять до приёмки; данных и секретов в Git быть не должно.
