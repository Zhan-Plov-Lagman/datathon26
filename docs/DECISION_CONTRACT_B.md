## Контракт фактов для A

Операционные определения true/false/null, кадры и границы: [FACT_DEFINITIONS_B.md](FACT_DEFINITIONS_B.md). Формат действующего входа: [RULES_B.md](RULES_B.md).

| Поле | Положительное основание | Что не является основанием |
| --- | --- | --- |
| `bank_cash_acceptance` | Установлен контекст приёма различимых наличных от клиента | Любая передача предмета или банковская обстановка |
| `actor_is_cashier` | Прослеживается обслуживающий участник именно этой операции; необходимый внешний контекст подтверждён человеком | Место за столом, одежда, распознавание лица |
| `cashier_left_workplace` | Прослежено физическое пересечение подтверждённой границы рабочего места | Поворот головы, другой клиент, исчезновение за перекрытием |
| `service_in_progress` | На момент ухода есть проверяемое основание незавершённости того же обслуживания | Предположение из отсутствия видимого чека |
| `service_completed` | До ухода подтверждено завершение того же обслуживания | Пауза, исчезновение клиента или отсутствие действий в редкой выборке |

Для каждого bool A сохраняет локально основания и ссылки на исходные PTS; неизвестное остаётся null. Официальная роль и граница рабочего места не выводятся из внешности. Источник внешнего контекста хранится отдельно. `service_in_progress=true` вместе с `service_completed=true` на один момент — конфликт, который требует проверки, а не автоматического rejected. Другие несовместимые основания также требуют проверки. Нынешний движок не выявляет такие конфликты автоматически: до передачи пакета нужен отдельный контроль, который A/B ещё должны реализовать и проверить.

Один пакет — одна операция, один участник и один эпизод. Начало — подтверждённый переход наружу; конец — возврат или последняя видимая граница эпизода с отметкой усечения. Anchor — реальный кадр, подтверждающий уход. Перекрывающиеся окна одного эпизода объединяются, повторный уход после возврата остаётся отдельным эпизодом. Нынешний B вычисляет start/end по охвату ссылок: это контекст, не точная сегментация; дедупликация эпизодов пока не реализована.

A должен подтвердить реализацию пакетов, происхождение контекста, обработку конфликтов, уточнение и семантику эпизодов отдельным коммитом и локальным прогоном. Наличие этого проекта не является согласием A.

## Условия окончательного решения

Следующая таблица задаёт целевую политику, а не уже готовую функцию. До валидации она не активна.

| Состояние после анализа | Внутренний результат | Основание для C |
| --- | --- | --- |
| Есть хотя бы одно проверенное событие активного класса, применимость и обязательные факты true, исключения false; нет конфликтов, уточнение и доказательства достаточны | supported | После проверки исходных JPEG и целостности анализа допустим положительный ответ. Неизвестность другого эпизода сама по себе не отменяет доказанное событие |
| Проверено отсутствие событий во всём согласованном охвате, все условия отрицательной политики ниже выполнены | negative eligible | Только после отдельной валидации политики допустим `no_violation` |
| Нет supported, но есть неизвестный факт, неразрешённый кандидат, недостаточный обзор/контекст или непокрытый класс | insufficient_data | Ни положительный, ни отрицательный публичный вывод не обоснован |
| Не удалось декодировать/выполнить анализ, нарушен формат, истёк бюджет обработки | technical_failure | Техническая ошибка; C применяет предусмотренный ТЗ failed |

Успешное получение observations не равно завершённому правовому анализу. Rejected одного кандидата не означает negative для видео. Для положительного события требуются отдельно проверенные исходные 1–3 JPEG и реальные времена; окончательные поля формирует C. Техническую неполноту нельзя замаскировать положительным частичным результатом с `complete=True`.

## Основания для «нарушений нет»

Версия будущей политики: `negative-policy.draft.v1`; **не передавать её в production `negative_policy_version`**. Строка версии не доказывает проверку.

Необходимы одновременно:

1. Явно зафиксирован перечень классов, для которых обещается отрицательный вывод. Проверка только ухода не доказывает отсутствие всех нарушений по ТЗ. Пока область общего `no_violation` не согласована с требованиями, глобальный отрицательный вывод запрещён.
2. Для каждого применимого класса есть проверенный детектор и отрицательная политика; неприменимость тоже имеет положительные основания, а не определяется отсутствием найденных событий.
3. Обзор всего ролика и уточнение обеспечивают достаточную видимость нужных стадий и границ. `complete=true`, `coverage_scope=full_video` и выполненные запланированные окна A не гарантируют этого: между выбранными кадрами возможны пропуски.
4. Все потенциальные эпизоды разрешены на основании фактов; нет relevant null, конфликтов, неподтверждённого контекста или неразрешённых кандидатов. Пустой список пакетов не является доказательством полноты поиска.
5. На независимых локальных примерах измерены пропуски, ложные тревоги, корректное воздержание, временная точность и полный бюджет; критерии допуска приняты A/B/C до финальной оценки.

Для ухода сложные отрицательные случаи проверяют физическое нахождение внутри установленной зоны, уход после подтверждённого завершения, подтверждённую неприменимость операции/роли. Нельзя сделать отрицательным случай, где завершение или зона просто не видны. Отрицание ухода также не отрицает другие классы.

## Недостаточность данных и ТЗ

В репозитории [CONTRACTS.md](CONTRACTS.md) отражает два публичных вердикта и технический failed. Отдельного разрешённого публичного исхода семантической неопределённости там нет. Оригинал ТЗ с указанием такого исхода в доступных документах не найден; нельзя утверждать, что требование организаторов уже согласовано.

Внутреннее состояние `insufficient_data` означает: обработка могла технически пройти, но фактов для правового вывода не хватает. Оно не сериализуется автоматически как failed или no_violation. A может уточнить контекст в оставшемся бюджете; человек может проверить локально при разработке. Если неизвестность остаётся, её нельзя устранить переименованием статуса.

До production C должен получить допустимое по исходному ТЗ решение для такого случая (либо согласованное уточнение организаторов), включая конечный статус и срок завершения. Нельзя оставлять принятые задания processing бессрочно. Пока это не решено, запуск production заблокирован; проверка readiness должна происходить до приёма заданий. Истечение реального технического дедлайна — отдельная техническая причина, но не обход семантической неопределённости.

## Что передаётся C сейчас

Существующий `rule_results.v1` остаётся внутренним результатом B. Не переименовывать его в `RuleDecision` и не выставлять complete/rules_reviewed по факту вызова функции. B принимает предложенное C разделение ответственности: A — факты/уточнение/кадры, B — проверка условий/политики, C — адаптер/API. Это согласие B на направление интеграции, не подтверждение готовности и не согласие других участников.

Для следующего проверенного контракта нужны: коммит извлекателя A; ревизия правил B; локальный отчёт по [LOCAL_VALIDATION_B.md](LOCAL_VALIDATION_B.md); зафиксированный охват отрицательного решения; согласованное поведение неизвестности; подтверждение C с коммитом адаптера и реальным сквозным прогоном. До этого C может интегрировать только документацию и синтетические проверки, не рабочую фабрику.
