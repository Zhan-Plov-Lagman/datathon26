# Скорость и качество: проверка L40S, 18 октября 2026

Это результаты разработки, а не независимая оценка точности и не готовый релиз сервиса. Веса загружены на арендованный командой сервер; анализ выполняется там самостоятельно, без облачного API модели. Банковские кадры, описания и подробные ответы остаются в закрытых артефактах.

## Измеренное сравнение до изменения контекста

Индексы в каталогах новых запусков могут отличаться; сравнивать по манифесту входов.

На X-14 при 8B FP16: CV 16,557 с, декодирование 3,438 с, VLM 13,841 с, 12 обзоров, без предложенных уточнений и повторов JSON. На X-47 два повтора JSON. NF4 8B потребовала 3 / 4 / 1 / 0 повторов в порядке столбцов. Состав кандидатов у моделей различался, поэтому это не равная точность при разной скорости. Все четыре 8B FP16 результата содержали ноль итоговых пакетов событий; ни одна из этих серий не подтвердила способность обнаруживать положительные случаи текущих классов. Число отсутствующих нарушений нельзя подменять технической долей успешных заданий.

Отдельные загрузки 8B NF4 и FP16 заняли 36,737 и 4,305 секунды в уже прогретом окружении. Это не обещание холодного старта: кэш файлов различался. GPU-память этих сравнительных запусков включала другие ещё загруженные модели; её нельзя выдавать за изолированный расход 8B.

## Что изменено в v1.4

- Плотное уточнение получает шесть кадров события и до шести исходных кадров родительского обзора. Реальные PTS, происхождение и границы события проверяются отдельно; редкие контекстные кадры не объявляются непрерывным наблюдением.
- Признак незавершённого обслуживания допускает явно незавершённый первоначальный приёмный пересчёт той же партии, а не только передачу денег. Ранее замеченный пересчёт, статичные предметы и пауза сами по себе этого не доказывают.
- Отдельный адаптер vLLM 0.11.0 использует официальную Qwen3-VL-32B-Instruct-FP8, закреплённую ревизию `4bf2c2f39c37c0fede78bede4056e1f18cdf8109`. Он проверяет локальный manifest/config, ограничивает JSON схемой, отвергает обрезанный или прерванный ответ и сохраняет общий дедлайн. Активный блокирующий `generate` прерывается внешним worker, а не внутренней проверкой времени.
- Первоначальная настройка 88% памяти не загрузилась: KV-кешу требовалось 2,00 ГиБ при доступных 1,56 ГиБ. Лимит повышен до 90%, контекст 8192 токена сохранён. Ошибка остаётся техническим отказом.
- Дополнительный агент обнаружил потерю строгой схемы из-за обёртки parser. Исправлена идентичность parser, добавлен тест реального вызова `review → VllmObserver`, включая повтор при неверной опоре события.

Окончательный связанный набор: **55 passed, 1 warning, 43,52 с** на Windows. Проверяются контекст/PTS, схема, ошибки, правила и API на синтетических данных. Отдельные тесты агентов входят в эту работу и не суммируются с 55 как независимые проверки.

## Выбор технологий

Для измеренной низкой задержки имеется `config/runpod-l40s-fast.env`: 8B FP16. Кандидат для проверки более крупной модели — `config/runpod-l40s-vllm.env`: 32B FP8. Между ними нет скрытого fallback; ошибка выбранной конфигурации не превращается в отрицательный вердикт.

NF4/AWQ/FP8 — способы представления весов; они не добавляют знания о нарушениях. Меньше бит не означает автоматически быстрее: в этой серии 8B FP16 заметно быстрее 8B NF4. vLLM выбран как проверяемый движок официальной FP8 модели. Отдельный TensorRT-LLM engine и неподтверждённые AWQ-веса не добавлены: их совместимость и польза здесь не измерены. Transformers использует SDPA; конкретный kernel FlashAttention не заявляется без проверки backend.

Первичные источники: [официальная FP8-модель Qwen](https://huggingface.co/Qwen/Qwen3-VL-32B-Instruct-FP8), [vLLM 0.11 sampling API](https://github.com/vllm-project/vllm/blob/v0.11.0/vllm/sampling_params.py), [нативная Qwen3-VL в vLLM](https://github.com/vllm-project/vllm/blob/v0.11.0/vllm/model_executor/models/qwen3_vl.py). Заявления авторов модели не заменяют проверку банковских видео.

## Что мешает заявить 99–100%

Проверены только четыре ранее выбранных файла, а не весь набор из 42 исходников. Реализованы две семьи фактов; охват всех нарушений ТЗ не завершён. Ни скорость, ни корректный JSON, ни крупная модель не подтверждают правильность фактов. Нужны проверенные положительные и сложные отрицательные случаи по классам, проверка таймкодов/JPEG и измерение ложных срабатываний и пропусков на отложенных данных. Настоящий реестр остаётся hypothesis; фиктивная запись приёмки не создавалась. Интеграционный API технически проверен, но реальный сервис распознавания по результатам этих тестов готовым не объявляется.

Приватные результаты: сервер `/workspace/forte/artifacts/development-unified/`; сравнение v1.3 — `run4`, `8b-comparison`, `8b-fp16`.

## Реальные прогоны vLLM

Первая технически успешная серия v1.4 с ограничением JSON-object до исправления выбора полной схемы: X-14 96,529 с; X-47 72,114 с; X-20 4,008 с; X-10 4,464 с. Загрузка 82,466 с. Все четыре завершены, повторов формата нет, полностью поддержанных фактами нарушений нет. Сравнение с v1.3 NF4 не изолирует эффект движка: одновременно отличается контекст v1.4.

Окончательный код с полной схемой прошёл реальную генерацию на L40S:

Все четыре задания завершены, загрузка 67,875 с. Полностью поддержанных фактами нарушений нет. Разницу 72,1 → 94,0 с нельзя приписать только компиляции схемы: её время отдельно не измерялось. Для трёх кандидатов извлечены три исходных JPEG; все декодированы, PTS точно совпали с опорными временами. Извлечение двух/одного JPEG заняло 1,222 / 0,542 с. Это доказательство происхождения изображения, а не доказательство правильности распознавания.

При отдельных опросах целого GPU наблюдалось до 43954 МиБ занятой памяти; это не непрерывное измерение пика. Counters PyTorch основного процесса не включают отдельный engine vLLM.

Ускорение 8B FP16 измерено; 32B FP8/vLLM реально работает с проверяемой схемой. Ни одна конфигурация по этим материалам не заслуживает заявления о 99–100% точности. Следующий шаг по качеству — разобрать пропуски и неизвестные факты на проверенных положительных случаях, подтвердить охват нужных классов и сравнить одинаковые версии на отложенной разметке. Повторная установка моделей или внедрение ещё одного движка сами по себе этот пробел не исправят.
