## 18 октября: арендованный L40S, большие модели

По отдельному запросу пользователя серверный кандидат повышен с Qwen2B до
**Qwen3-VL-32B-Instruct NF4**. Сравнительная Qwen8B также скачана. Это выбор
конфигурации для проверки; превосходство точности на банковских видео пока не измерено.
Локальная 4B завершила скачивание, но на ноутбуке ещё не проверялась.

Рабочая папка сервера `/workspace/forte`, код исходного снимка `7f4e107`.
Штатные torch 2.8.0+cu128 и torchvision 0.23.0+cu128 сохранены; зависимости
установлены в отдельную .venv. Повторяемый `scripts/setup_linux.sh` успешно выполнен.
После окончательной установки **182 passed, 6 subtests passed**, 22,08 с;
четыре предупреждения Starlette TestClient. Браузерные тесты на сервере не запускались.

Синтетический MOV, 3 с, четыре кадра 320×192, одинаковый observer/prompt/NF4:

| Проверка | Загрузка модели, с | Анализ после загрузки, с | Peak reserved, МиБ | Повторы JSON |
|---|---:|---:|---:|---:|
| 8B: первый запуск | 48,840 | 12,159 | 7908 | 0 |
| 8B: проверка с блокировкой Python sockets | 37,386 | 10,868 | 7908 | 0 |
| 32B: проверка с блокировкой Python sockets | 88,745 | 24,523 | 22034 | 0 |

32B помещается и возвращает валидные observations. Два разных запуска 8B
не усредняются в p95. На этом коротком примере 32B медленнее 8B; это не измерение
сравнительной точности. Кэш файлов и длительность ответа влияют на эти замеры.
Не обещать, что увеличение модели одновременно ускорит анализ и устранит ошибки.

RT-DETRv2, YOLO11m-pose и OWLv2 также скачаны непосредственно на сервер.
Синтетический CV-прогон с заблокированными Python sockets завершён:
RT-DETR 10 кадров / 1,052 с; YOLO 10 / 5,894 с; OWLv2 4 / 1,636 с.
Частота выборки соответственно 3, 3 и 1 fps, длительность 3 с; это время после
загрузки, с первым вызовом. Эти прогоны подтверждают работу адаптеров,
не преимущество модели или FPS на реальном потоке. Peak reserved: 866 / 494 / 2512 МиБ.

Дополнительная проверка обычных настроек: синтетический MOV 12 с / 1280×720,
шесть кадров на обзорное окно, max_long_edge=560. 32B NF4: analyze 19,799 с;
три плотных окна уточнения 57,537 с; вместе с исходными JPEG **77,658 с**.
Peak reserved 22032 МиБ, повторов JSON нет. Два JPEG декодированы как 1280×720,
PTS точно 0 и 11,9 с. Это проверка worker analyze/refine/evidence, без правил/API.
Отдельная загрузка модели заняла **190,009 с**; вместе с обработкой 267,667 с.
Разброс времени загрузки между прогонами большой: причину отдельно не профилировали.
Перед приёмом API-заданий модель должна быть загружена один раз в GPU-процесс;
холодный запуск не следует прятать в заявлении о готовности или p95.
Python-соединения были заблокированы и в этом прогоне.

Код, ревизии, команды и ограничения: `docs/RUNPOD_SETUP.md`.
`config/runpod-l40s.env` явно выбирает 32B для runtime и включает offline-режим;
не содержит ключей, не активирует hypothesis-правила и не запускает фиктивный сервис.
Исходные банковские данные на этом этапе на сервер не переносились.
Из кэша установки удалено 5,1 ГиБ лишнего скачанного CUDA/PyTorch-набора.

Следующее: соединить общий CV-поиск с адресной VLM-проверкой в реальном processor,
проверить факты и правила, затем измерить ошибки и полный API-сценарий на допустимых
размеченных данных. Qwen32B — рабочий кандидат, а не автоматически готовая система
обнаружения нарушений. Старые незавершённые пункты интеграции не закрываются сменой GPU.
