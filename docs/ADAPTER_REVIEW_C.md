## Форма адаптера принята C с уточнениями

```python

bundle = worker.assess(video_path, report, timeout_sec=remaining,
                       deadline=deadline, local_context=local_context)

```

`worker.assess` пока отсутствует. Не добавлять вызов в runtime, не выставлять FORTE_RULES_FACTORY на тестовую фабрику. Технический прототип A с bool/null и синтетическими тестами можно разрабатывать до активации правил.

Внешний интерфейс C сохраняется: factory возвращает объект с `evaluate(report, *, video_path, worker, deadline) -> RuleDecision`. C реализует эту обёртку после готовности извлекателя и политики. Внутри она проверяет bundle, вызывает B, применяет согласованную политику; исходные JPEG затем пакетно извлекает существующий IntegratedProcessor. `app.rules:evaluate` напрямую фабрикой не является. Нельзя превращать `public_verdict_ready=false` в True простым переименованием полей.

## Конкретные уточнения к результату A

Сигнатуру менять не требуется. Просьба A зафиксировать следующие поля оболочки перед реализацией; имена ниже — предложение C, ожидающее ответа A/B:

- `schema_version: "assessment_bundle.v1"`, `report`, `assessments`, `diagnostics`. Пакеты assessments сохраняют действующую схему B; дополнительные сведения хранятся отдельно.
- `report` сохраняет исходные windows и идентификаторы и добавляет уточнения с уникальными window_id. Все observation_refs, включая ссылки диагностики, разрешаются в этом выходном отчёте. Идентичность видео/job/model сохраняется. Уточнение интервала не превращается в full_video без исходного обзора.
- `diagnostics.episodes`: один элемент на `(rule_id, event_id)`, стабильный идентификатор операции/участника внутри видео без идентификации личности, границы эпизода в реальных PTS, признаки усечения/потери прослеживания, `conflicts`, причины неизвестности. Контекстный охват observation_refs нельзя выдавать за точные границы ухода.
- `diagnostics.episodes[].fact_sources`: для каждого факта происхождение `visual`, `local_context` или `unknown`; для visual — observation_refs; для local_context — идентификатор и версия локального подтверждения/ревью, отдельно от визуальных ссылок. Полное содержимое контекста остаётся локальным. Значение bool без прослеживаемого основания не допускается к окончательному решению.
- `diagnostics.search`: `assessed_rule_ids`, `unresolved_episode_ids`, ограничения обзора и контекста. Это сведения для политики B, не самостоятельное доказательство отсутствия нарушений. Пустые assessments не означают успешный отрицательный анализ.

`service_in_progress=true` и `service_completed=true` в один момент должны сохраняться как выявленный конфликт и блокировать решение по эпизоду до уточнения. Не передавать такой пакет в текущий B как обычный rejected: движок пока не распознаёт конфликт. A обнаруживает и сообщает конфликт, C проверяет его перед вызовом B; перечень противоречий задаёт B. Противоречащие источники нельзя молча свести к false.

Один экземпляр observer, общий абсолютный deadline, timeout_sec не больше оставшегося бюджета. В бюджет входят последующие правила и JPEG. Технический сбой пробрасывается; bool/null и ограничения возвращаются как данные. Повторные окна одного эпизода объединяются A до B; C проверяет уникальность ключа, но не угадывает эпизоды по близости времени. `full_sequence_visible` остаётся отдельным смысловым утверждением.

## Ответ C на decision-policy.draft.v1 B

C принимает разделение ответственности и условия проекта B:

| Ситуация | Предлагаемое поведение адаптера |
| --- | --- |
| Проверенное событие активного правила, достаточные основания, нет конфликта по событию, анализ технически завершён | RuleDecision с supported; затем проверка 1–3 исходных JPEG и окончательный violation. Неизвестность другого эпизода сама по себе не отменяет доказанное событие |
| Нет supported и выполнена отдельно проверенная отрицательная политика для согласованного охвата | RuleDecision с пустым supported и настоящей negative_policy_version; затем no_violation |
| Нет supported, остались null/конфликты/неразрешённые эпизоды или недостаточный охват | Внутреннее insufficient_data; публичное отображение пока НЕ согласовано |
| Декодирование/модель/формат/технический deadline нарушены | Техническое исключение, итог failed; частичный успех не выдаётся |

В оригинале ТЗ указаны processing/done/failed и violation/no_violation; отдельного публичного insufficient_data не задано. C не добавляет третий вердикт и не подменяет неизвестность техническим сбоем либо отрицательным ответом. Нужен ответ организаторов о допустимом конечном исходе технически обработанного, но неоднозначного видео. Нельзя держать его processing бессрочно или специально дожидаться таймаута. Пока вопрос не решён, production-фабрика не активируется. Это не запрещает реализацию и локальную проверку извлекателя.

`negative-policy.draft.v1` нельзя использовать как production negative_policy_version. Проверка одного ухода не обосновывает общий отрицательный ответ. Охват и критерии допуска фиксирует B с командой до оценки; C проверяет метаданные и согласованную политику, не придумывает нормативные критерии.
