**Прототип assessments, 18 октября — не production.** Добавлен настоящий метод:

Оболочка согласована по форме с C: `schema_version=assessment_bundle.v1`, `report`, `assessments`, `diagnostics.episodes` с `fact_sources` и `diagnostics.search`. При неизвестной идентичности actor_id/operation_id остаются null; C должен учитывать unresolved_episode_ids. Один реальный технический прогон прошёл за 19,641 с и принят B, но все факты неизвестны и событие человеком не подтверждено.

```python
# Тот же worker, ранее полученный report и тот же видеофайл.
# deadline остаётся общим для analyze, assess и последующих стадий.
bundle = worker.assess(video_path, report, timeout_sec=120,
                       deadline=deadline, local_context=None)
result = evaluate(bundle["report"], bundle["assessments"], registry)
```

Метод повторно декодирует реальные PTS из входного отчёта и вызывает ту же локальную Qwen с отдельным коротким промптом визуального движения. Юридические bool модель больше не обязана генерировать: значения по умолчанию null; если claims возвращены, сохраняются только как непроверенная диагностика. Новые наблюдения добавляются в копию отчёта под уникальными window_id. Пакеты ссылаются на **выходной** report. Код дополняет временные ссылки наблюдениями, покрывающими предложенный интервал; это не подтверждение смысла действия. Одиночная строка ограничения сохраняется в списке без удаления текста. В диагностике — предложения границ перехода, конфликт стадий обслуживания и причина неизвестности каждого факта. Консольный вывод сцены запрещён; сохранять bundle только в `artifacts`. Метаданные/PTS сверяются с видео, но это не криптографическая проверка идентичности: вызывающий обязан передать исходную пару видео/отчёт одного задания.

**Существенные ограничения:** все пять значений в `assessments[].facts` сейчас принудительно null. Проверка локального контекста, геометрии, функциональной роли, непрерывности передачи и адаптивное уточнение ещё не реализованы. Это работающий генератор визуальных предложений и пакетов неизвестности, не детектор подтверждённых фактов. Переданный ненулевой local_context отклоняется явно, а не игнорируется. `refinement_complete=false`, `full_sequence_visible=false`. Повторный просмотр тех же кадров не называется уточнением. Правила не активируются, результат не содержит публичного вердикта.

В каждом окне модель предлагает максимум один переход; идентификатор имеет семантику **предположения об эпизоде**. Пересекающиеся предложения остаются только в диагностике, без склейки и без двух пакетов. Межоконное прослеживание участника/операции не решено; непересекающиеся предложения также нельзя считать подтверждённым числом разных эпизодов. Пустой результат не обосновывает no_violation. Техническое complete означает, что все запрошенные окна обработаны. Ошибки формата/PTS/декодирования/дедлайна пробрасываются, worker освобождает блокировку. На синтаксическую ошибку JSON разрешён один повтор в том же бюджете.

Для C: можно проверять формат на синтетических данных; рабочую фабрику/readiness этим методом не активировать. Для B: следующий результат — локальное подтверждение зоны и примера разработки, затем реализация/проверка разрешения отдельных null. Это отдельный этап, не скрытая готовность нынешнего прототипа.

Существующий файл результата не перезаписывается. Консоль показывает только успешность, число окон, время и GPU-память. Содержимое наблюдений сохраняется локально и не должно передаваться облачному ИИ, включая копирование JSON в чат помощнику.

Для подробного просмотра выбранного интервала добавить `--start-sec 10 --end-sec 18 --frames 12`. Числа в примере синтетические. При необходимости `--max-long-edge 848` сохраняет исходное разрешение для рассматриваемого набора; расход памяти и время измерять отдельно.

Нормальный выход содержит `schema_version: observations.v1`, `analysis_kind: observations_only`, `complete: true`, `coverage_scope`, метаданные видео, окна наблюдений и технические метрики. `complete` означает обработку всех запланированных окон, а не просмотр каждого кадра или достоверность всех действий. `interval` не является проверкой всего ролика.

При технической ошибке процесс завершается ненулевым кодом и записывает `complete: false` с классом ошибки. Это не отрицательный вердикт. Дедлайн отсчитывается от начала `analyze`, после загрузки модели; CLI отдельно сообщает `model_load_sec`. Координатор должен учитывать время очереди и выдачи при расчёте общего пяти­минутного бюджета.

Если модель нарушила синтаксис JSON, выполняется один повтор с теми же кадрами и требованием более короткого ответа. Он не продлевает дедлайн. Ошибка схемы, включая неверные индексы кадров, или повторная ошибка прерывает анализ. `generation.attempts` в окне показывает число попыток, `metrics.format_retries` — накопительное число повторов в этом GPU-процессе. Это технические показатели, не оценка уверенности.

Проверка времени внутри генерации кооперативная: она срабатывает между шагами. Для жёсткого ограничения C должен контролировать GPU-процесс снаружи и завершать зависшее задание по общему дедлайну.

**Программный стык для B и C.**

Проверка опубликованных веток B/C, воспроизводимые синтетические тесты и оставшиеся разрывы описаны в [INTEGRATION_A.md](INTEGRATION_A.md). Python-интерфейс A/C проверен; автоматическое извлечение пакетов фактов B и фабрика evaluator ещё не готовы.

Для интеграции использовать один `LocalGPUWorker` на GPU-процесс. Он переиспользует модель и не допускает одновременных операций: при занятости выбрасывает `WorkerBusy`, а C оставляет следующее задание в очереди. Это локальный Python-интерфейс; сетевой транспорт и хранение заданий реализует C.

```python
import time
from app.inference.qwen import QwenObserver
from app.inference.worker import LocalGPUWorker

# Один раз при старте процесса, до приёма заданий:
worker = LocalGPUWorker(QwenObserver("models/Qwen3-VL-2B-Instruct-shards"))

# C передаёт оставшийся бюджет, уже с учётом очереди и резерва на выдачу.
deadline = time.monotonic() + remaining_budget_sec
overview = worker.analyze(video_path, job_id, deadline=deadline)
# B выбирает интервалы для повторного просмотра; пример ниже синтетический.
refined = worker.refine(video_path, job_id, [
    {"candidate_id": "candidate-1", "start_sec": 10.0, "end_sec": 18.0}
], deadline=deadline)
# B проверяет уточнённые наблюдения и выбирает реальные опорные времена.
evidence = worker.evidence(video_path, {"candidate-1": [anchor_sec]}, deadline=deadline)
```

Переменные `remaining_budget_sec`, `video_path`, `job_id`, `anchor_sec` приходят от C/B; пример показывает стык, а не готовый нормативный анализ. Число `time.monotonic()` нельзя передавать между разными ноутбуками: на принимающей машине создать собственный дедлайн из оставшегося бюджета. На этом же процессе все стадии используют один дедлайн. Локальные лимиты по умолчанию — до 240 с на обзор и до 120 с на весь список уточнений; раньше всегда срабатывает общий дедлайн. Наружный контроль процесса по-прежнему обязателен для жёсткого ограничения.

`refine` возвращает `refinements.v1`, `complete`, `analysis_kind: observations_only`, `refinements: [{candidate_id, report}]`. `report` — обычный `observations.v1`. Уточнение использует окна 4 с, перекрытие 1 с и 6 кадров, до 560 px по длинной стороне: выборка в три раза плотнее обзорной по интервалу между кадрами полного окна. Интервалы проверяются до генерации; одинаковые пары границ обрабатываются один раз, но сохраняют связь с каждым кандидатом. Ошибка любого интервала прерывает весь вызов. `complete` не является подтверждением нарушения.

`evidence` принимает словарь `идентификатор события -> 1–3 времени`, за один проход извлекает кадры для всех событий и возвращает словарь с теми же ключами. Дубликаты фактических кадров удаляются внутри события. JPEG сохраняют исходное разрешение; отбор опорных кадров остаётся за B после уточнения. Низкоуровневые функции также доступны:

```python
from app.inference.qwen import QwenObserver
from app.inference.pipeline import LocalVideoAnalyzer
from app.evidence.frames import extract_evidence

# При старте GPU-процесса:
observer = QwenObserver("models/Qwen3-VL-2B-Instruct-shards")
analyzer = LocalVideoAnalyzer(observer)

# Внутри одного задания, без параллельных вызовов на этом GPU:
observations = analyzer.analyze(video_path, job_id, timeout_sec=210)
# B получает observations["windows"] и возвращает проверенные события.
# После выбора события:
frames = extract_evidence(video_path, [event_anchor_sec])
# C собирает публичный результат только после успешной проверки правил.
```

`event_anchor_sec` и результаты правил в примере — точки подключения будущей реализации, а не готовый код оценки. Для доказательств также передавать абсолютный monotonic-дедлайн через параметр `deadline`. Окна могут повторять одно событие; объединение событий выполняется после правил, не по совпадению свободного текста модели.

Наблюдение содержит `start_frame`, `end_frame`, `start_sec`, `end_sec`, `description`. Индексы локальны для окна; времена вычисляются кодом из реальных кадров, не принимаются на веру от модели. `operation_context` — краткое описание ситуации; `visibility_limits` — список ограничений обзора. Эти поля содержат банковский контент и остаются локальными.


Одна модель и один worker обслуживают шесть случаев: корректный вход, синтетический повреждённый файл, корректный вход после ошибки, уже истёкший дедлайн, лимит 3 с, корректный вход после дедлайнов. Выбирать ролик, обработка которого заведомо дольше 3 с; иначе короткий лимит может законно не вызвать ожидаемый отказ, и проверка сообщит несовпадение. Не совмещать `--stability` с `--refine`.

После каждой попытки записываются только технические метрики в `stability-metrics.json`, так что завершённые измерения сохраняются даже при последующем сбое. Полные успешные ответы пишутся отдельно и остаются локальными. `expected_outcome` показывает соответствие ожидаемому результату: ожидаемый отказ остаётся `complete: false`. Любое несовпадение даёт ненулевой код выхода после всей серии. Проверка не подменяет ошибки успешными ответами.

Пики VRAM сбрасываются перед каждой попыткой только для измерения; после неё записываются `idle_allocated_mib` и `idle_reserved_mib`. Выполняется сборка мусора Python и синхронизация CUDA, но не очистка CUDA-кэша и не перезагрузка модели. Это позволяет заметить удержание тензоров после ошибок. Короткая серия не доказывает отсутствие утечек на длительной нагрузке и не заменяет контроль процесса C.

Техническая основа: [Qwen3-VL в Transformers](https://huggingface.co/docs/transformers/en/model_doc/qwen3_vl), [квантование bitsandbytes](https://huggingface.co/docs/transformers/quantization/bitsandbytes), [локальная установка PyTorch](https://pytorch.org/get-started/locally/).
