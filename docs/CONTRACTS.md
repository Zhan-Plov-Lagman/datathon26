# Контракты приложения

Это согласуемый контракт первой реализации для участников A, B и C. Он не означает, что перечисленные методы уже работают. Обязательные поля API взяты из ТЗ; внутренние структуры и HTTP-коды ниже — предлагаемые решения команды.

Реализация C в `feature/api-ui` сохраняет эту публичную схему. Предложенный закрытый транспорт и адаптер правил описаны в [WORKER_TRANSPORT.md](WORKER_TRANSPORT.md); A/B должны проверить их при интеграции. Запуск — [DEPLOYMENT.md](DEPLOYMENT.md), сверка оригинального ТЗ — [CASE_CHECKLIST_C.md](CASE_CHECKLIST_C.md). Синтетические проверки C не подтверждают готовность модели или нормативного вердикта.

**Публичный API принадлежит C.**

`POST /api/v1/analyze`: заголовок `X-API-Key`, multipart-поле `file`, видео MOV. Предлагаемый успешный HTTP-код 202, тело `{"job_id":"<opaque-id>"}`. Сначала надёжно сохранить файл и задание, затем ответить. Тяжёлый анализ идёт в отдельном процессе.

`GET /api/v1/jobs/{job_id}`: тот же заголовок. Пока задание выполняется, HTTP 200 и `{"job_id":"<opaque-id>","status":"processing"}`. Внешний статус покрывает также ожидание в очереди.

Завершённый результат без событий:

```json
{
  "job_id": "synthetic-example",
  "status": "done",
  "verdict": "no_violation",
  "violations": []
}
```

При наличии событий `verdict` равен `violation`, список непустой. Каждое событие содержит:

| Поле | Тип и условие |
| --- | --- |
| `type` | Непустая строка из согласованного каталога типов |
| `timecode_sec` | Конечное число от нуля до длительности видео |
| `description` | Наблюдаемое действие, связь с правилом, название документа, пункт и URL |
| `evidence_frames` | От одного до трёх объектов |
| `evidence_frames[].timestamp_sec` | Реальное время соответствующего кадра в секундах |
| `evidence_frames[].image_base64` | JPEG в base64 без префикса `data:` |

При технической ошибке GET возвращает HTTP 200 и `{"job_id":"<opaque-id>","status":"failed"}`. Дополнительную публичную структуру ошибки согласовать отдельно; подробный traceback, пути и секреты не отдавать клиенту. Предлагаемые HTTP-коды для ошибок запросов: 401 для неверного ключа, 404 для неизвестного job_id, 413 для превышения лимита загрузки, 422 для неподдерживаемого или невалидного входа. Конкретные лимиты загрузки и длительности согласовать с ТЗ и тестовыми файлами, не ограничивать их ровно наблюдавшимся максимумом.

Сбой анализа не становится `no_violation`. Для семантической неопределённости третьего вердикта в опубликованной схеме нет. Внутренние причины неопределённости сохраняются отдельно; они не отменяют положительный вердикт, если другое событие подтверждено.

**Наблюдения принадлежат A, правила принадлежат B.**

Вход анализа: локальный путь к загруженному видео, идентификатор задания, конфигурация и предельное время завершения. Модуль анализа не читает файл разметки и не классифицирует по имени файла.

Выход наблюдений одного окна:

| Поле | Смысл |
| --- | --- |
| `window_start_sec`, `window_end_sec` | Границы окна по оригинальному видео |
| `frame_timestamps` | Реальные времена переданных кадров |
| `observations` | Наблюдаемые действия с временем, временными идентификаторами участников и ссылками на кадры |
| `visibility_limits` | Что закрыто, плохо различимо или находится за пределами записи |

Временные идентификаторы участников обозначают объекты внутри ролика и не устанавливают личность. Не использовать распознавание лиц.

Правила получают наблюдения и контекст операции, возвращают кандидатов: `rule_id`, `start_sec`, `end_sec`, `anchor_sec`, ссылки на наблюдения, проверенные условия, исключения и внутреннее решение `candidate`, `supported` либо `rejected`. Эти значения не являются публичными вердиктами.

Только `supported` попадает в итоговый список. Перед этим A уточняет время и извлекает кадры; B проверяет смысловой шаблон; C сериализует результат по общей схеме. Если уточнение требует нового просмотра, кандидат остаётся внутренним до завершения проверки. Нельзя автоматически превращать выданное моделью число уверенности в вероятность.

Реализация A в `feature/ml-worker` уточняет структуру: каждое наблюдение содержит `start_frame`, `end_frame` (индексы в окне), вычисленные по реальным кадрам `start_sec`, `end_sec` и `description`. Окно также содержит `operation_context`. Общий отчёт имеет версию `observations.v1`, признаки `analysis_kind: observations_only`, `complete` и `coverage_scope: full_video | interval`. Эти поля не меняют публичную схему жюри. Подключение описано в `docs/WORKER.md` из ветки A.

**Координатор принадлежит C, обработчики запускают A и B.**

На первой интеграции C может вызвать локальный анализ на одной машине. Затем внедряется закрытый обмен заданиями: выдать свободному обработчику задание с арендой, передать файл в контур обработчика, принимать heartbeat, получить результат, проверить и атомарно завершить задание. Конкретные внутренние URL согласуют A и C перед реализацией; они не являются публичными маршрутами жюри.

Незавершённое задание после отказа можно переназначить, если остаётся временной бюджет. Повторы ограничены; результаты привязаны к попытке. Поздний ответ старой попытки не перезаписывает уже принятый результат. Учебный хеш применяется для контроля данных; хеш входа не используется для подстановки организаторской метки.

**Общий порядок проверки.**

Сначала проверить контракт на явно синтетическом примере без банковских данных. Затем пройти настоящий ролик локально. Затем тот же сценарий выполнить через публичный API и проверить декодирование JPEG из его ответа. Заглушки не включать в рабочую выдачу жюри. Изменения обязательных полей согласовывать со всеми тремя участниками.
