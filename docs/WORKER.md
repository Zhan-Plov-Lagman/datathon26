# Локальный обработчик роли A

**Текущий прототип, 18 октября: departure-visual.v0.4.** Сначала модель ищет предложения движения в обзорных окнах; структурированные признаки извлекаются только при плотном уточнении: одного ли участника она прослеживает, видимую передачу/обработку наличных, переход, положение стоп и незавершённую передачу по кадрам. Это предположения локальной модели, качество пока не измерено. Геометрический расчёт может выдать bool при наличии проверенного локального контекста; иначе сохраняет null.

```python
import time

remaining_sec = deadline - time.monotonic()  # общий бюджет задания
bundle = worker.assess(video_path, report, timeout_sec=remaining_sec,
                       deadline=deadline, local_context=None)
# После согласования готовности детектора и реестра с B/C:
# decision = finalize_bundle(report, bundle,
#     supported_rule_ids=["cashier_leaves_service"], registry=registry)
```

Метод использует тот же worker, модель и общий deadline. Проверяет метаданные и реальные PTS исходного видео. Вызывающий отвечает за принадлежность пары видео/отчёт одному заданию. Исходные окна остаются неизменными; новые наблюдения добавляются с уникальными ID. Ссылки assessments относятся к выходному bundle.report. Ошибка декодирования, формата или дедлайна пробрасывается; успешного receipt при ней нет. На ошибку JSON или структуры — один повтор для каждой стадии в том же бюджете. Повтор получает напоминание о точной схеме и допустимых индексах; повторная ошибка остаётся отказом.

**diagnostics.search:** schema_version=detector_execution.v1, job_id, detector_runs и дополнительный execution_trace. Запись содержит rule_id, detector_version, status=complete, processed_window_ids всех исходных/добавленных окон. Trace связывает каждую пару окон с действительно завершёнными стадиями: visual_candidate; dense_candidate/dense_features только при уточнении; predicate_evaluation. visual_features появляется только в явном техническом режиме без уточнения. Исходное и обзорное окно используют те же PTS; плотные окна содержат собственные реальные времена. Receipt создаётся после реального поиска кандидатов во всех обзорных окнах и всех назначенных уточнений. В v0.4 при отсутствии кандидата вызов признаков не выполняется и не записывается как выполненный. При наличии кандидата признаки извлекаются на плотных кадрах; лишний обзорный вызов признаков исключён. Вызов одного build_bundle без исполненного прохода не создаёт detector_runs.

**Уточнение v0.4:** для каждого предложенного anchor назначается окно до 4 с (±2 с, обрезается границами видео), шесть кадров с исходными PTS. На них повторяются отдельные стадии движения и признаков. Одинаковые интервалы одного исходного окна обрабатываются один раз. Исходные окна и новые обзорные наблюдения сохраняются; плотные окна получают отдельные ID. Пакеты строятся по результатам уточнения, а обзорные предложения не дублируются. Если уточнение убрало предложение, это видно в refinements[].remaining_proposals. Все назначенные просмотры имеют общий deadline, ошибка любого из них отменяет успешный bundle.

refinement_status=completed означает завершение всех назначенных просмотров; not_needed — в этом проходе не было назначений. В пакетах уточнённого результата refinement_complete=true, однако full_sequence_visible=false: шесть кадров не доказывают непрерывную видимость. Четырёхсекундный предел может не охватить весь переход; качество этого выбора ещё не измерено. Trace содержит исходный output_window_id и refinement_window_ids, а processed_window_ids покрывает все сохранённые окна. Версия v0.4 совместима с формой B 03a1f31 / C 476976c.

Модель по-прежнему просят кратко выделить одно движение, но корректный список из нескольких предложений (не больше числа промежутков между кадрами) не отбрасывается: каждое получает уточнение. Пересекающиеся события не склеиваются в выдуманную идентичность и остаются неподтверждёнными. ID предложения включает его порядковый номер, поэтому несколько предложений одного окна не делят event_id.

Массив неправильной длины исправляется только если ВСЕ его элементы null: он превращается в массив null нужной длины с записью _normalizations и метрикой unknown_array_repairs. Известные координаты/значения не обрезаются, не сдвигаются и не дополняются; такой ответ остаётся ModelOutputError. Диагностика ошибки содержит только типы и числа, без модельного текста.

**Необязательный local_context:** локальный словарь, не файл меток и не ответ для подстановки. Реальные контексты не коммитить. Текущая расширенная форма A требует согласования с B:

- schema_version: local_context.draft.v1; непустые view_id, context_version, reviewer, reviewed_at, basis_ref;
- coordinate_space: normalized_display_after_rotation;
- scope: job_id и display_width, display_height, rotation именно этого задания после поворота;
- workplace_polygon: null либо многоугольник из нормализованных [x,y]; adjacent_equipment_included: bool/null;
- cash_context_confirmation и functional_role_confirmation: необязательные {value: bool/null, basis_ref: непустая строка}; подтверждение относится к этому заданию и обрабатывающему наличные участнику;
- max_transition_gap_sec: необязательный положительный предел между соседними опорными кадрами. Это экспериментальный параметр локальной проверки, не утверждённый B критерий непрерывности. Без него уход/продолжение обслуживания остаются null.

Без контекста все пять итоговых фактов неизвестны. Контекст сам по себе не заменяет видимую передачу/обработку денег. Уход требует соседних кадров, явно наблюдаемого перехода, положения стоп внутри/снаружи подтверждённой зоны; закрытые стопы и точка на границе дают null. Незавершённая передача на обеих сторонах перехода поддерживает service_in_progress=true и service_completed=false только при остальных положительных условиях. Завершение передачи не доказывает завершение обслуживания; service_completed=true не выставляется. fact_sources сохраняет mixed/unknown, ссылки и основание контекста. Разреженные кадры не доказывают отсутствие скрытого промежуточного завершения — это ограничение прототипа, требующее проверки/уточнения.

Пересекающиеся предложения остаются диагностическими, без склейки. Межоконное прослеживание не реализовано. Публичного вердикта в bundle нет, public_verdict_ready=false. Неизвестность не превращается в false; отрицательное решение разрешается только согласованной политикой B/C после готового поиска.

Нормальный выход содержит `schema_version: observations.v1`, `analysis_kind: observations_only`, `complete: true`, `coverage_scope`, метаданные видео, окна наблюдений и технические метрики. `complete` означает обработку всех запланированных окон, а не просмотр каждого кадра или достоверность всех действий. `interval` не является проверкой всего ролика.

При технической ошибке процесс завершается ненулевым кодом и записывает `complete: false` с классом ошибки. Это не отрицательный вердикт. Координатор должен учитывать время очереди и выдачи при расчёте общего пяти­минутного бюджета.

Если модель нарушила синтаксис JSON, выполняется один повтор с теми же кадрами и требованием более короткого ответа. Он не продлевает дедлайн. Ошибка схемы, включая неверные индексы кадров, или повторная ошибка прерывает анализ. `generation.attempts` в окне показывает число попыток, `metrics.format_retries` — накопительное число повторов в этом GPU-процессе. Это технические показатели, не оценка уверенности.

Проверка времени внутри генерации кооперативная: она срабатывает между шагами. Для жёсткого ограничения C должен контролировать GPU-процесс снаружи и завершать зависшее задание по общему дедлайну.

**Программный стык для B и C.**

Проверка опубликованных веток B/C, воспроизводимые синтетические тесты и оставшиеся разрывы описаны в [INTEGRATION_A.md](INTEGRATION_A.md). Python-интерфейс A/C проверен; автоматическое извлечение пакетов фактов B и фабрика evaluator ещё не готовы.

Для интеграции использовать один `LocalGPUWorker` на GPU-процесс. Он переиспользует модель и не допускает одновременных операций: при занятости выбрасывает `WorkerBusy`, а C оставляет следующее задание в очереди. Это локальный Python-интерфейс; сетевой транспорт и хранение заданий реализует C.

```python
import time
from app.inference.qwen import QwenObserver
from app.inference.worker import LocalGPUWorker

# Один раз при старте процесса, до приёма заданий:
worker = LocalGPUWorker(QwenObserver("models/Qwen3-VL-2B-Instruct-shards"))

# C передаёт оставшийся бюджет, уже с учётом очереди и резерва на выдачу.
deadline = time.monotonic() + remaining_budget_sec
overview = worker.analyze(video_path, job_id, deadline=deadline)
# B выбирает интервалы для повторного просмотра; пример ниже синтетический.
refined = worker.refine(video_path, job_id, [
    {"candidate_id": "candidate-1", "start_sec": 10.0, "end_sec": 18.0}
], deadline=deadline)
# B проверяет уточнённые наблюдения и выбирает реальные опорные времена.
evidence = worker.evidence(video_path, {"candidate-1": [anchor_sec]}, deadline=deadline)
```

Переменные `remaining_budget_sec`, `video_path`, `job_id`, `anchor_sec` приходят от C/B; пример показывает стык, а не готовый нормативный анализ. Число `time.monotonic()` нельзя передавать между разными ноутбуками: на принимающей машине создать собственный дедлайн из оставшегося бюджета. На этом же процессе все стадии используют один дедлайн. Локальные лимиты по умолчанию — до 240 с на обзор и до 120 с на весь список уточнений; раньше всегда срабатывает общий дедлайн. Наружный контроль процесса по-прежнему обязателен для жёсткого ограничения.

`refine` возвращает `refinements.v1`, `complete`, `analysis_kind: observations_only`, `refinements: [{candidate_id, report}]`. `report` — обычный `observations.v1`. Уточнение использует окна 4 с, перекрытие 1 с и 6 кадров, до 560 px по длинной стороне: выборка в три раза плотнее обзорной по интервалу между кадрами полного окна. Интервалы проверяются до генерации; одинаковые пары границ обрабатываются один раз, но сохраняют связь с каждым кандидатом. Ошибка любого интервала прерывает весь вызов. `complete` не является подтверждением нарушения.

`evidence` принимает словарь `идентификатор события -> 1–3 времени`, за один проход извлекает кадры для всех событий и возвращает словарь с теми же ключами. Дубликаты фактических кадров удаляются внутри события. JPEG сохраняют исходное разрешение; отбор опорных кадров остаётся за B после уточнения. Низкоуровневые функции также доступны:

```python
from app.inference.qwen import QwenObserver
from app.inference.pipeline import LocalVideoAnalyzer
from app.evidence.frames import extract_evidence

# При старте GPU-процесса:
observer = QwenObserver("models/Qwen3-VL-2B-Instruct-shards")
analyzer = LocalVideoAnalyzer(observer)

# Внутри одного задания, без параллельных вызовов на этом GPU:
observations = analyzer.analyze(video_path, job_id, timeout_sec=210)
# B получает observations["windows"] и возвращает проверенные события.
# После выбора события:
frames = extract_evidence(video_path, [event_anchor_sec])
# C собирает публичный результат только после успешной проверки правил.
```

`event_anchor_sec` и результаты правил в примере — точки подключения будущей реализации, а не готовый код оценки. Для доказательств также передавать абсолютный monotonic-дедлайн через параметр `deadline`. Окна могут повторять одно событие; объединение событий выполняется после правил, не по совпадению свободного текста модели.

Наблюдение содержит `start_frame`, `end_frame`, `start_sec`, `end_sec`, `description`. Индексы локальны для окна; времена вычисляются кодом из реальных кадров, не принимаются на веру от модели. `operation_context` — краткое описание ситуации; `visibility_limits` — список ограничений обзора. Эти поля содержат банковский контент и остаются локальными.

**Проверка кода без банковского контента.**

```powershell
& .\.venv\Scripts\python.exe -m unittest discover -s tests/worker -v
& .\.venv\Scripts\python.exe -m scripts.smoke_worker
```

Тесты создают синтетическое видео, проверяют переменные временные интервалы, реальное время JPEG, поворот, границы окон, невалидный ответ и отсутствие ложного публичного вердикта. Они не подтверждают качество самой модели; для этого нужен отдельный локальный прогон с человеческой оценкой.

Технический прогон самого короткого и самого длинного локальных MOV, без чтения разметки и без вывода сцен в консоль:

```powershell
& .\.venv\Scripts\python.exe -m scripts.benchmark_worker --video-dir '<папка с MOV>' --output-dir artifacts/benchmark-run1
```

Для каждого нового прогона выбирать новый выходной каталог. `metrics.json` содержит только технические показатели; остальные файлы в этом каталоге содержат банковские данные и не передаются облачным помощникам. Успех этого прогона подтверждает исполнение и формат, но не точность обнаружения нарушений.

Для проверки обзора, одного выбранного по времени интервала и пакетного извлечения доказательств с общим бюджетом добавить к команде технического прогона `--refine`. Интервал берётся из середины ролика без чтения меток и не объявляется нарушением.

Текущие ограничения: обзорная редкая выборка может пропускать быстрые действия; B должен передать кандидатов в готовый метод уточнения и проверить его результат; нет сетевого транспорта заданий C; модель может вернуть неподдерживаемый JSON, и тогда задание явно завершится ошибкой. Метрики реального запуска и проверенные версии фиксируются в `docs/HANDOFF_A.md` после выполнения.

**Последовательные задания и восстановление после ошибок.**

```powershell
& .\.venv\Scripts\python.exe -m scripts.benchmark_worker --video '<уже использованный для разработки MOV>' --output-dir artifacts/stability-run-new --stability
```

Одна модель и один worker обслуживают шесть случаев: корректный вход, синтетический повреждённый файл, корректный вход после ошибки, уже истёкший дедлайн, лимит 3 с, корректный вход после дедлайнов. Выбирать ролик, обработка которого заведомо дольше 3 с; иначе короткий лимит может законно не вызвать ожидаемый отказ, и проверка сообщит несовпадение. Не совмещать `--stability` с `--refine`.

После каждой попытки записываются только технические метрики в `stability-metrics.json`, так что завершённые измерения сохраняются даже при последующем сбое. Полные успешные ответы пишутся отдельно и остаются локальными. `expected_outcome` показывает соответствие ожидаемому результату: ожидаемый отказ остаётся `complete: false`. Любое несовпадение даёт ненулевой код выхода после всей серии. Проверка не подменяет ошибки успешными ответами.

Пики VRAM сбрасываются перед каждой попыткой только для измерения; после неё записываются `idle_allocated_mib` и `idle_reserved_mib`. Выполняется сборка мусора Python и синхронизация CUDA, но не очистка CUDA-кэша и не перезагрузка модели. Это позволяет заметить удержание тензоров после ошибок. Короткая серия не доказывает отсутствие утечек на длительной нагрузке и не заменяет контроль процесса C.
